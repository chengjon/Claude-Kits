## 模式 1: 需求澄清

### 何时使用

- 用户请求不明确或有多种解释
- 需要技术决策（框架、工具、架构选择）
- 缺少关键实现细节
- 可能存在多种合理方案

### 对话流程

```
用户请求
    ↓
识别歧义点
    ↓
使用 AskUserQuestion 工具
    ↓
获取用户选择
    ↓
基于选择继续实施
```

### 示例 1: 功能实现澄清

```markdown
用户: 添加一个登录功能

助手: 我需要了解几个细节：

[使用 AskUserQuestion 工具]

1. **认证方式**？
   - [ ] 用户名/密码（需要实现注册和密码重置）
   - [ ] OAuth2（Google, GitHub等第三方登录）
   - [ ] JWT token（无状态认证，适合API）
   - [ ] 其他

2. **是否需要注册功能**？
   - [ ] 是，完整的注册流程
   - [ ] 否，仅登录（用户由管理员创建）

3. **密码重置**？
   - [ ] 通过邮箱
   - [ ] 管理员重置
   - [ ] 不需要

4. **会话管理**？
   - [ ] Cookie-based session
   - [ ] JWT token
   - [ ] Redis session store
```

**用户回答后**:

```markdown
助手: 明白了。我将实现：
- JWT token 认证
- 完整注册流程（含邮箱验证）
- 邮箱密码重置
- Redis session 存储

[使用 TodoWrite 规划任务]
[开始实施]
```

### 示例 2: 技术选型澄清

```markdown
用户: 需要实时通知功能

助手: 关于实时通知的实现方式：

[使用 AskUserQuestion 工具]

1. **通知频率**？
   - [ ] 高频（每秒多次更新）→ WebSocket
   - [ ] 中频（每分钟几次）→ Server-Sent Events
   - [ ] 低频（偶尔推送）→ 长轮询

2. **客户端类型**？
   - [ ] 仅Web浏览器
   - [ ] Web + 移动应用
   - [ ] 多种客户端

3. **消息类型**？
   - [ ] 文本通知
   - [ ] 包含富媒体（图片、视频）
   - [ ] 结构化数据

4. **离线支持**？
   - [ ] 需要，离线时缓存通知
   - [ ] 不需要，仅在线推送
```

### 示例 3: 性能要求澄清

```markdown
用户: 优化这个查询

助手: 了解几个关键指标：

1. **当前性能**：
   - 查询耗时多少？
   - 数据量有多大？
   - 并发量如何？

2. **目标性能**：
   - 期望的响应时间？
   - 未来数据增长预期？

3. **约束条件**：
   - 是否可以修改表结构？
   - 是否可以添加缓存层？
   - 数据库版本？

[基于回答选择优化策略：索引 vs 缓存 vs 分区 vs 重构]
```

### 最佳实践

#### DO（推荐）

1. **一次性询问所有必要信息**
   - ✅ 避免来回多次询问
   - ✅ 使用 AskUserQuestion 工具提供选项
   - ✅ 为每个选项提供清晰的描述

2. **提供默认推荐**
   ```markdown
   推荐：JWT token + Redis session（适合你的微服务架构）
   ```

3. **解释选项含义**
   - 每个选项的优缺点
   - 适用场景
   - 影响范围

#### DON'T（避免）

1. ❌ **不要问显而易见的问题**
   ```markdown
   ❌ 错误:
   用户: 添加用户搜索
   助手: 你确定要添加搜索功能吗？

   ✅ 正确:
   助手: 搜索字段：用户名、邮箱，还是都支持？
   ```

2. ❌ **不要分批询问相关问题**
   ```markdown
   ❌ 错误:
   助手: 认证方式？
   用户: JWT
   助手: [实施一半] 需要注册功能吗？
   用户: 需要
   助手: [再修改] 密码重置呢？

   ✅ 正确:
   助手: [一次性询问所有相关问题]
   ```

3. ❌ **不要提供过多选项（> 4 个）**
   - 用户选择困难
   - 使用分组或分层询问
