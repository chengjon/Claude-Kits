## 模式 4: 方案建议

### 方案结构

```
列出 2-4 个可行方案
    ↓
每个方案：
  - 优点
  - 缺点
  - 适用场景
  - 实施成本
    ↓
基于上下文给出推荐
```

### 示例 1: 技术选型

```markdown
用户: 如何存储用户头像？

助手: 3 种常见方案：

**方案 1: 数据库 BLOB**
- 优点:
  - 实现简单，无需额外服务
  - ACID 保证，事务一致性
- 缺点:
  - 数据库体积快速增长
  - 查询性能下降
  - 备份时间增加
- 适用: < 1000 用户，内部系统
- 成本: 低（无额外服务费用）

**方案 2: 文件系统**
- 优点:
  - 读写快速
  - 实现简单
  - 零成本
- 缺点:
  - 扩展性差（单服务器限制）
  - 备份复杂
  - 无 CDN 加速
- 适用: 单服务器部署，中小规模
- 成本: 低（仅存储成本）

**方案 3: 对象存储（S3/OSS/COS）**
- 优点:
  - 高可用（99.99%）
  - 无限扩展
  - CDN 加速
  - 自动备份
- 缺点:
  - 需要配置和集成
  - 有使用成本（但不高）
  - 依赖外部服务
- 适用: 生产环境，需要扩展
- 成本: 中（$0.023/GB/月 + 流量费）

**推荐**: 方案 3（对象存储）

**原因**:
1. 你的项目已部署在 AWS → 使用 S3 集成方便
2. 预期用户增长 → 需要扩展性
3. 成本可控 → 1000 用户约 $5/月

**实施步骤**:
1. 创建 S3 bucket
2. 配置 IAM 权限
3. 集成 AWS SDK
4. 实现上传/下载 API
5. 配置 CloudFront CDN

需要帮你实施吗？
```

### 示例 2: 架构决策

```markdown
用户: 应该使用微服务还是单体架构？

助手: [先了解项目情况]
[
  Read('package.json'),
  Glob('src/**/*.ts', head_limit=20)
]

助手: 基于你的项目情况（3个开发者，MVP阶段）：

**方案 1: 单体架构**
- 优点:
  - 开发速度快
  - 部署简单
  - 调试容易
  - 无分布式复杂性
- 缺点:
  - 未来拆分需要重构
  - 扩展粒度粗
- 推荐度: ⭐⭐⭐⭐⭐
- 原因: **现阶段最佳选择**

**方案 2: 模块化单体**
- 优点:
  - 单体的简单性
  - 清晰的模块边界
  - 未来可平滑过渡到微服务
- 缺点:
  - 需要严格的模块纪律
- 推荐度: ⭐⭐⭐⭐
- 原因: 好的折中方案

**方案 3: 微服务**
- 优点:
  - 独立扩展
  - 技术栈灵活
- 缺点:
  - 开发/运维复杂度高
  - 需要服务发现、负载均衡、分布式追踪
  - 团队需要 DevOps 能力
- 推荐度: ⭐⭐
- 原因: **过度设计**，3人团队难以维持

**结论**:
建议方案 1（单体架构），但采用模块化设计：

```
src/
  modules/
    user/
    order/
    payment/
```

未来如果需要（用户 > 100K，团队 > 10人），可以按模块拆分为微服务。
```

### 方案建议原则

#### 1. 了解上下文

```markdown
关键上下文：
- 团队规模
- 技术能力
- 时间约束
- 预算限制
- 当前架构
- 未来规划
```

#### 2. 量化对比

```markdown
✅ 好的对比:
方案A: 实施时间 2天，成本 $100/月，性能 100ms
方案B: 实施时间 5天，成本 $50/月，性能 50ms

❌ 模糊对比:
方案A: 快但贵
方案B: 慢但便宜
```

#### 3. 给出明确推荐

```markdown
✅ 明确推荐:
推荐方案 B，因为：
1. 性能提升 2x
2. 长期成本更低
3. 符合未来扩展需求

❌ 模糊推荐:
两个方案都不错，看你的需求...
```
